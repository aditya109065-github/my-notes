Foundations: ACID & Transaction States

Core Theory
Definition
A Transaction is a logical unit of work consisting of a sequence of database operations, while ACID is the set of properties ensuring that such units are processed reliably despite failures.
Key Points
  • Atomicity — The "All-or-Nothing" execution. Managed by the Transaction Manager.
  • Consistency — Transitions between valid states. Responsibility of the Application Programmer.
  • Isolation — Independent execution of concurrent transactions. Managed by the Concurrency Control Manager.
  • Durability — Persistence of committed data in non-volatile storage. Responsibility of the Recovery System.
  • State Transitions: Active → Partially Committed → Committed → Terminated.
  • Point of No Return: Once the Committed state is reached, effects are durable and cannot be rolled back.
Formulas & Rules
PropertyMeaning & Implementation
AtomicityT must execute all operations or none. Requires rollback logs.
ConsistencyTotal balance before T must equal total balance after T.
IsolationConcurrent execution must produce results identical to some serial T₁, T₂...Tₙ.
DurabilityCommitted data must survive a crash via write-ahead logging (WAL) to disk.
Comparison: Abort vs. Commit
FeatureAbort / RollbackCommit
Integrity ActionUndoes all partial changes.Makes all changes permanent.
State ResultDatabase returns to previous consistent state.Database moves to new consistent state.
Recovery PathCan be Restarted or Killed.Finalized; persists in non-volatile memory.
Things to Remember
⚠️
Common Trap: Students misattribute "Consistency" to the DBMS. The Application Programmer is responsible for consistency logic (e.g., ensuring a transfer deducts X and adds X).
💡
Partially Committed Volatility: A system crash during Partially Committed stage results in a Failed state because the buffer is cleared before the write-to-disk completes.
🔑
Key Insight: Atomicity forces reversal of partial changes (e.g., a $100 transfer failing after debiting but before crediting is rolled back by Atomicity, not Consistency).

Relational Algebra & Relational Calculus

Query Languages
Definition
Relational Algebra is a procedural language using operators to transform relations, while Relational Calculus is a non-procedural language based on first-order predicate logic.
Key Points
  • Basic Operators: Selection (σ), Projection (π), Union (∪), Set Difference (−), Rename (ρ), Cartesian Product (×).
  • Derived Operators: Joins (⋈), Intersection (∩), and Division (÷).
  • Union/Difference Constraints: Relations must be "Union-Compatible" (identical attribute sets and domains).
  • Projection Duplication: Relational Algebra (π) automatically removes duplicate tuples, unlike SQL.
Formulas & Rules
OperatorSymbolPurpose / Logic
Selectionσcond(R)Filters rows satisfying a predicate.
Projectionπattr(R)Filters columns; removes duplicates.
UnionR ∪ SCombines rows from two compatible relations.
Cartesian ProductR × SEvery row in R paired with every row in S.
Comparison: Algebra vs. Calculus
FeatureRelational AlgebraRelational Calculus
ParadigmProcedural (Steps)Non-Procedural (Logic)
ImplementationOperator-basedVariable and Predicate-based
Internal UseQuery OptimizationQuery Specification
Things to Remember
⚠️
Common Trap: Never confuse Selection (σ) with Projection (π). Selection is a horizontal filter (rows); Projection is a vertical filter (columns).
🔑
Join = Product + Selection: An Inner Join is logically equivalent to a Cartesian Product followed by a Selection: σR.id=S.id(R × S).
💡
Result Size: |R × S| = |R| × |S|. If |R| = 10 and |S| = 5, the product yields 50 tuples.

Functional Dependencies, Axioms & Closure

Schema Analysis
Definition
Functional Dependency (X → Y) states that X uniquely determines Y; Attribute Closure (X⁺) is the set of all attributes that can be derived from X using a given set of FDs.
Key Points
  • Armstrong's Axioms: Reflexivity (if Y ⊆ X then X → Y), Augmentation (if X → Y then XZ → YZ), Transitivity (if X → Y, Y → Z then X → Z).
  • Secondary Rules: Union, Decomposition, Composition, and Pseudo-transitivity.
  • Prime Attribute: Part of at least one Candidate Key.
  • Candidate Key (CK): A minimal Super Key (no proper subset is a Super Key).
Formulas & Rules
Dependency TypeLogic ConditionExample
TrivialY ⊆ X{ID, Name} → {ID}
Non-TrivialY ⊄ X{ID} → {Name}
Semi Non-TrivialX ∩ Y ≠ ∅{ID, Dept} → {Dept, Building}
Comparison: Super Key vs. Candidate Key
FeatureSuper KeyCandidate Key
PropertyUniqueness onlyUniqueness + Minimality
RelationshipAll CKs are Super KeysNot all Super Keys are CKs
Things to Remember
⚠️
Key Trap: A Super Key does not have to be minimal. If {ID} is a CK, then {ID, Age} is a Super Key but not a Candidate Key.
🔑
Closure Algorithm: 1. Initialize Result = X. 2. For each FD A → B, if A ⊆ Result, then Result = Result ∪ B. 3. Repeat until no more changes.
💡
GATE Problem Walkthrough: R={E,F,G,H,I,J,K,L,M,N}. FDs: EF→G, F→IJ, EH→KL, K→M, L→N. Find key → {E,F,H}⁺ yields all attributes — minimal set, so answer is {E,F,H}.

Normalization: 1NF – BCNF

Schema Design
Definition
Normalization is the formal process of refining a database schema through a hierarchy of rules (1NF to BCNF) to minimize redundancy and prevent update anomalies.
Key Points
  • 1NF: All attributes must be atomic; no multi-valued attributes.
  • 2NF: Must be 1NF + No Partial Dependencies (Non-prime attributes must depend on the entire CK).
  • 3NF: Must be 2NF + No Transitive Dependencies (Non-prime attributes must not depend on other non-prime attributes).
  • BCNF: A stricter 3NF. For every X → Y, X must be a Super Key.
  • Golden Rule: Every BCNF is 3NF, but not every 3NF is BCNF. 3NF allows X → Y if Y is a prime attribute; BCNF does not.
Formulas & Rules
Normal FormTarget to EliminateCondition for X → Y
2NFPartial DependencyX is not a proper subset of CK
3NFTransitive DependencyX is Super Key OR Y is Prime
BCNFAny key-determinant violationX must be a Super Key
Comparison: Normalization vs. Denormalization
FeatureNormalization (OLTP)Denormalization (OLAP)
GoalConsistency and IntegritySearch Performance and Speed
Anomaly RiskLowHigh (requires app-level handling)
Things to Remember
⚠️
Common Trap: Students miss the "Prime Attribute" exception in 3NF. If X → Y and Y is prime, 3NF is satisfied even if X is not a superkey. BCNF removes this exception.
🔑
1NF Violation: If a "Student" table has a "Phone" column containing multiple numbers, it violates 1NF (non-atomic attributes).

Mathematics of Keys: Super Key Calculations

Combinatorics
Definition
The Number of Super Keys is the total count of attribute sets that contain at least one Candidate Key.
Key Points
  • If a relation R has n attributes and a CK has k attributes, any set formed by adding any of the remaining (n−k) attributes to that CK is a Super Key.
  • The total number of subsets of a relation is 2ⁿ. The set of all attributes is always the largest Super Key.
Formulas & Rules
ScenarioFormula
One CK with k attributes2n−k
Maximum Possible Super Keys2n − 1
Two CKs (A, B)SK(A) + SK(B) − SK(A ∪ B)
Three CKs (A, B, C)∑SK(Aᵢ) − ∑SK(Aᵢ∩Aⱼ) + SK(A∩B∩C)
Things to Remember
⚠️
Inclusion-Exclusion: Always subtract intersections when counting multiple CKs. Overlapping CKs (e.g., {A,B} and {A,C}) require careful union calculation {A,B,C} to avoid double-counting.
🔑
120 Super Keys Walkthrough: R(A,B,C,D,E,F,G,H) with CKs: AD, BD, ED, FD. n=8, k=2. Each CK has 2⁶=64 → 4×64=256. Subtract 6 pairs (2⁵=32 each) → −192. Add 4 triples (2⁴=16 each) → +64. Subtract quad (2³=8) → −8. Result: 256−192+64−8 = 120.

Concurrency Control & Scheduling

Transaction Mgmt
Definition
Concurrency Control is the management of simultaneous transaction execution to ensure Serializability — maintaining the illusion of serial execution despite interleaving.
Key Points
  • Conflict Serializability: A schedule is conflict-serializable if it can be transformed into a serial schedule by swapping non-conflicting operations.
  • Conflicts: Two operations conflict if they belong to different transactions, access the same data, and at least one is a Write.
  • Dirty Read: Reading data from an uncommitted transaction.
  • Lost Update: T₁ and T₂ update X; T₁'s update is overwritten.
Formulas & Rules
MetricFormula
Total Serial Schedules (n transactions)n!
Total Schedules (nᵢ ops in Tᵢ)(∑nᵢ)! / ∏(nᵢ!)
Comparison: Schedule Types
Schedule TypeCommittal Rule
RecoverableTⱼ commits only after Tᵢ (where Tⱼ read from Tᵢ) commits.
CascadelessTⱼ cannot read X until the previous writer Tᵢ commits.
StrictTⱼ cannot read OR write X until the previous writer Tᵢ commits.
Comparison: Protocols
ProtocolOverheadStrategic Advantage
Lock-based (2PL)High (Lock Table management)Guarantees conflict serializability
Timestamp-basedModerate (Ordering logic)Avoids deadlocks; uses TS(T) for order
Things to Remember
⚠️
Serializability Subset: Conflict-Serializable ⊂ View-Serializable. All conflict-serializable schedules are view-serializable, but view-serializability allows "blind writes" that conflict-serializability might reject.
🔑
2PL Phases: Growing (acquire locks, no release) → Lock Point (peak) → Shrinking (release locks, no acquire). Deadlock detection uses a Wait-for Graph (cycle = deadlock).

Storage & Indexing Structures

Physical Optimization
Definition
Indexing is a physical storage optimization using an Index-table (Search Key + Block Pointer) to minimize query search time by reducing disk block accesses.
Key Points
  • Search Key: The attribute set used to sort the index.
  • Data Reference (Block Pointer): The address of the disk block containing the actual tuple.
  • Primary Index: Sorted data, unique key.
  • Clustered Index: Sorted data, non-unique key.
  • Secondary Index: Data not necessarily sorted; uses candidate keys.
Comparison: Index Structures
FeatureB+ TreeBitmap
ImplementationBalanced TreeBit-strings
Search SpeedO(log n)O(1) for Boolean ops
Best CaseHigh Cardinality (Unique IDs)Low Cardinality (Gender, Boolean)
OverheadHigh during insertion/deletionHigh for high-cardinality data
Comparison: Dense vs. Sparse Index
FeatureDense IndexSparse Index
Entry RuleEvery search key has an entryOnly some keys (one per block)
SpeedFast (direct lookup)Requires secondary search within block
SpaceSpace-intensiveSpace-efficient
Things to Remember
⚠️
Secondary Index Penalty: Secondary Indexing is always slower than Primary Indexing. Primary index directs to the sorted record; Secondary index may scatter records across blocks, causing multiple I/O seeks.
💡
B+ Tree Advantage: B+ Trees are better than B-Trees for range queries because linked leaf nodes allow sequential traversal without backtracking.

Ultimate Revision Summary

30-Second Digest
Key Points
  • ACID Responsibility: Atomicity (Tx Manager), Consistency (Programmer), Isolation (Concurrency), Durability (Recovery).
  • Transaction Path: Active → Partially Committed (Buffer) → Committed (Disk).
  • Algebra Symbols: σ (Rows), π (Columns), × (n × m Tuples).
  • Closure Algorithm: Recursive set expansion to find Super Keys and CKs.
  • Normalization Goals: 1NF (Atomic), 2NF (No partial), 3NF (No transitive), BCNF (Determinant = Super Key).
  • Super Key Formula: 2ⁿ⁻ᵏ for single key; Inclusion-Exclusion for multiple.
  • Concurrency Problems: Dirty Read (Uncommitted), Lost Update (Overwrite), Inconsistent Read (Mid-Tx change).
  • 2PL Phases: Growing (Locking), Shrinking (Unlocking). Lock Point is the peak.
  • Indexing Speed: Primary > Secondary. B+ Trees > B-Trees (for range). Dense > Sparse (speed).
  • Key Truths: Cascadeless forbids reading uncommitted; Strict forbids reading/writing uncommitted. BCNF is always 3NF. All CKs are Super Keys. Total serial schedules = n!.
